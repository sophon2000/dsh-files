## 0. 一句话结论

**这批改动的功能方向是对的，但最大瓶颈不在性能、不在功能，而在「插件自己重新发明了宿主已有的三层基础设施」——路径解析、字节/时间格式化、查询串解析。** 三处自建实现各自产生了可复现的缺陷：`DSH_HOME=~` 时扫描错目录、面板与模型工具对同一文件报出不同大小、以及一个 49 行的手写查询串解析器。删掉它们、复用宿主真源，能同时消灭 4 个 bug 和约 60 行代码。

## 1. 重新定义问题（第一性原理）

用户问的是「最大瓶颈在哪」。先消解这个问题本身——它有三个互不等价的读法，必须分开回答，否则会得到「哪里都优化一点」的废话：

| 读法 | 层面 | 本次审查的答案 |
|---|---|---|
| A. 运行时性能瓶颈 | 单机开销 | **不是瓶颈**。全库扫描实测 2ms（13 条目），下载走流式，无 N+1 |
| B. 正确性瓶颈 | 会不会出错 | **是瓶颈**。3 个可复现缺陷，1 个扫描错目录（功能性） |
| C. 架构瓶颈 | 长期维护成本 | **是最大瓶颈**。自建宿主已有设施，导致缺陷会随宿主演进而复发 |

**关键判据**：C 是 A 和 B 的根因。3 个缺陷里有 2 个（路径解析、格式化）的成因完全相同——「宿主已经有真源了，插件又写了一遍」。所以本次审查的结论不是「修 3 个 bug」，而是**「消除让 bug 反复产生的那类写法」**。

## 2. 最大瓶颈：三处对宿主基础设施的重复实现（P0）

### 2.1 `defaultAttachmentsDir()` 重新发明 `resolveDshHome`（功能性缺陷）

`src/attachments.ts:35-42` 手写了 `.dsh` 家目录解析。宿主在 `@deepseek-ai/dsh-home-paths` 里有唯一真源 `resolveDshHome(configured?, env?)`，附件存储自身就是这样算根的：

```js
// dsh-attachment-local/lib/index.js:986
this.root = resolve(join(resolveDshHome(config.dshHome), "attachments", "v1"));
```

实测对比 9 个输入（`node /tmp/rootcmp.mjs`），**3 处发散**：

| `DSH_HOME` | 插件算出 | 真源算出 | 后果 |
|---|---|---|---|
| `~` | `~/.dsh/attachments/v1` | `~/attachments/v1` | **扫错目录，面板永远空** |
| `relative/home` | `relative/home/...`（相对路径） | `/cwd/relative/home/...` | 依赖进程 cwd，非确定性 |
| `~\sub` | `~\sub/attachments/v1`（未展开） | `~/sub/attachments/v1` | Windows 形态不展开 |

- `DSH_HOME=~` 一行配置就能让整个附件闭环静默失效，且不报错（目录不存在按空清单处理）。
- 相对路径那条更隐蔽：同一份配置在 web 进程里可能解析到不同目录，属不可复现类 bug。

**修法（code judo）**：删掉整个函数，改
```ts
import { resolveDshHome } from '@deepseek-ai/dsh-home-paths'
const attachmentsDir = config.attachmentsDir.trim() !== ''
  ? config.attachmentsDir
  : join(resolveDshHome(), 'attachments', 'v1')
```
减 8 行代码，同时获得 `configured` 参数、`~\` 展开、空值防呆。**这是净删除复杂度的改动，应无条件采纳。**

### 2.2 字节/时间格式化三处重复，且已经发散（显示不一致）

同一个概念存在三份实现：`src/attachments.ts:152`（服务端）、`src/attachments/ref.ts:73`（服务端，`formatTime`）、`src/client/index.tsx:305,312`（客户端）。

实测（`node /tmp/fmtcmp.mjs`）：

| 字节数 | 模型工具 `attachment_list` | 面板 `formatBytesClient` |
|---|---|---|
| 3 GiB | `3072.0 MB` | `3.00 GB` |
| 900 GiB | `921600.0 MB` | `900.00 GB` |

即 **模型在 `attachment_list` 里看到「3072.0 MB」，用户在同一面板看到「3.00 GB」**——同一个文件的两个数字。`formatTime` 两份暂时巧合一致，但已无任何机制保证继续一致。

另：客户端 `formatTimeClient` 用 `getFullYear/getMonth/...`（本地时区），而 `src/attachments/ref.ts:76` 的实现同样取本地字段却**注释写的是 `Compact UTC display timestamp`**（`ref.ts:72`）——注释与实现相悖，注释是错的。

**修法**：抽 `src/format.ts` 单一实现（`formatBytes` 统一走 GB 分支、`formatTime` 明确本地时区并改注释），服务端与客户端共用。客户端经 esbuild 打进 bundle，无额外体积代价。

### 2.3 `readQuery()` 手写查询串解析（16 行换 3 行）

`src/attachment-loop.ts:55-70` 用 `indexOf('?name=')` / `indexOf('&name=')` 手写解析（16 行），三个路由各用一次。我按对抗性思路试了字符串包含、二次编码、`&` 注入等输入（`node --input-type=module -e ...`）：

```
/x?ref=has%26q%3Dinjected  -> "has&q=injected"   // 先切分后解码，未被打穿
/x?ref=a%20%26q%3Dnope     -> "a &q=nope"        // 同上
```

**结论：没被攻破**（切分在解码之前，这个顺序恰好挡住了注入）。但它仍是净负债：

- 16 行自建逻辑，服务于 3 个调用点；`URLSearchParams` 需要 3 行且是标准语义。
- 行为偏差：`+` 不按空格解码（`?q=a+b` → `"a+b"`），而 `URLSearchParams` 给 `"a b"`——当前无影响，属埋在未来的语义分歧。
- 未来若有人「顺手修一下」这个函数（比如把解码提前），注入就成立了。**当前安全是巧合，不是设计。**

**修法**：
```ts
const search = new URL(req.url ?? '', 'http://local').searchParams
const q = search.get('q') ?? undefined
```
`queryInt` 随之简化为 `Number.parseInt(search.get(name) ?? '', 10)` + `Number.isInteger` 守卫（保留原有的负数/越界钳制语义）。

## 3. 低级 bug 清单（按严重度）

### P0-1 `DSH_HOME=~` 扫错目录
见 §2.1。功能性、静默、一行配置触发。

### P0-2 `tsc --noEmit` 失败，但 `npm test` 通过
```
test/attachment.test.ts(113,42): error TS2345: Argument of type '{}' is not assignable
  to parameter of type 'ToolRunContext'.  (×6 处)
```
- `package.json` 的 `test` 脚本只有 `node --test`，**不带类型检查**；`build` 脚本的 `tsconfig.build.json` 只 include `src`，**排除 `test`**。
- 结果：**类型错误只在开发者的编辑器里可见，`npm test` 永远绿**。这是最典型的「测试给你虚假信心」的结构问题。
- 修法二选一：给 `test` 加 `tsc --noEmit && node --test`；或把测试里的 `{}` 显式断言成 `ToolRunContext`。**建议前者**——门禁应覆盖全套。

### P0-3 `exportToWorkspace` 把整个文件读进内存
`src/attachment-loop.ts:136-144`：
```ts
const chunks: Uint8Array[] = []
for await (const chunk of attachments.readFileStream({...})) chunks.push(chunk)
await fsp.writeFile(dest, Buffer.concat(chunks))
```
- 官方 seam 是**流式**的（`readFileStream` 返回 `AsyncIterable`），这里却全量缓冲再 `Buffer.concat`——等于主动放弃流式的意义。
- 上限是 `maxDownloadBytes` 默认 **200 MiB**，即单个附件可一次性吃掉 200 MiB 堆（concast 时是 2×：chunks + 拼接结果）。
- 对比：**下载路由**（`attachment-loop.ts:246-256`）正确地逐块写 `res` 并处理背压。两条路径都传字节，一条流式一条全量——同一文件里两种写法，是明显的不一致。
- 修法：改用 `createWriteStream` + 逐块 `write`（或 `pipeline`），与服务端另一条路径对齐。同时天然获得部分写失败时不留半个文件的行为（当前 `writeFile` 已是原子替换，改造时需保持这一点）。

### P1-4 面板只显示 `files/`，看不到图片附件（覆盖缺口）
实测 `~/.dsh/attachments/v1` 五个子树：

| 子树 | 文件数 | 大小 | 插件是否读取 |
|---|---|---|---|
| `files/` | 14 | 2.4 MB | ✅ |
| `file-objects/` | 14 | 0B（硬链接镜像，link count=2） | — （正确跳过，否则重复计数） |
| `objects/` | **24** | **13.7 MB** | ❌ **未读** |
| `request-images/` | 1 | 0.8 MB | ❌ 未读 |

- `objects/` 是**图片附件的规范化对象**（`normalizedImagePath` = `objects/<sha2>/<sha>`），`request-images/` 是请求态图片缓存。
- 即 **全库 17MB 里 14.5MB（85%）面板完全不可见**。README 说「列出全部附件（名/大小/时间/sha）」，实际只说对了一半：只列出**文件类**附件。
- 这是设计层缺口，不是笔误：`listAttachments()` 从第一行就只 `join(dir,'files')`。`objects/` 无原始文件名（文件名在会话事件里，不在磁盘上），所以「按原名显示」这条路径对图片不成立——需要走官方的会话事件 API 取名字，成本明显更高。
- **建议**：这属于「要么补齐、要么如实声明」的二选一。如果不动 `objects/`，必须把 README/CHANGELOG 里「列出全部附件」改成「列出文件类附件（不含图片）」，否则是**对用户的能力误述**。

### P1-5 `@` 源在无 llm 服务时静默消失
`src/client/index.tsx:487` 过滤 `row.handle !== undefined`，而 `handle` 来自 `attachment_list` 路由的 `deps.llm?.fileRequestText`（`attachment-loop.ts:83-90`）。llm 服务缺席时全表 `handle === undefined` → 候选为空 → **@ 菜单里那一组直接不出现，零提示**。
- 用户视角：功能「不存在」，无法区分「没附件」和「服务没接上」。
- 修法：候选为空时给出可诊断信息，或在注册失败路径统一提示（目前 `index.ts:129-131` 只在注册抛错时 `console.warn`，静默降级无 UI 痕迹）。

### P2-6 前端搜索是服务端往返，未去抖
`src/client/index.tsx:392-395`（`search` → `load`）+ `:423`（`onChange`）：每个按键一次 `fetch`。
- 已用 `seq`（`index.tsx:344,350`）做了竞态防护 ✅，但**没有 debounce**：输入「合同」触发 2 次请求，每个请求在服务端做一次全库扫描 + 全量 JSON 序列化。
- 讽刺的是：客户端**已经持有了全量数据**（`fetchAttachments('')` 一次取 `limit=300` 条，全部在 `items` 里），然后**带着查询串回服务端请求同样的数据再过滤一遍**。服务端的 `pageOf` 过滤（`attachment-loop.ts:100`）对客户端过滤而言是纯冗余。
- 当前 13 条目无感，但这是「数据量一上来就变卡」的写法。修法：`useMemo` 客户端过滤（`pageOf` 保留给 API 消费者），或至少加 200ms debounce。

### P2-7 `?q=` 的 `+` 不解码为空格（见 §2.3）

### P2-8 响应泄漏内部状态
`src/attachment-loop.ts:306`：
```ts
json(res, 400, { error: 'session has no workspace cwd', debug: `found=${session !== undefined} session=${sessionId}` })
```

`debug` 字段把内部对象状态和 sessionId 回给浏览器。虽在信任栅栏之后（同源/回环），但 400 响应里出现 `debug` 键属开发期残留，应删或降为服务端日志。

## 5. 附件库应该放在哪（用户直接提问）

**现状**：宿主 0.1.5-rc.1 的附件库真源是 `resolveDshHome()/attachments/v1`（内容寻址，五子树），插件通过**只读扫描 `files/`** 去理解它。

**判定：位置本身没问题，问题在「插件自己算这个位置」和「自己解析这个布局」。**

三条路，按推荐度：

1. **（推荐）继续只读扫描，但根路径改用 `resolveDshHome`，并诚实声明覆盖范围。**
   即 §2.1 的修法 + P1-4 的 README 措辞修正。理由：`AttachmentStore` 是公开 seam，但它的**方法面只有 save/read**——没有 list/delete/TTL（官方注释自认 retention 是 future work）。**「列出有什么」这件事官方确实没提供**，所以插件补这一块是**正当的**，不是重复造轮子。要改的只是「不要重复实现根解析」和「不要假装覆盖了图片」。

2. **（进阶）用官方 `ctx.attachments` + 会话事件 API 替代目录扫描。**
   即 0.6.1 设计文档 §4.1 原本规划、但最终改成了「0.6.0 的只读目录扫描」的那条路。代价：需要遍历 `SessionStore.list()` + `Session.ownEvents()` 提取 `FileAttachmentRef`，代码量显著增加；收益：不再耦合磁盘布局（`files/<sha2>/<sha>/<name>`），宿主改布局不会静默失效，且**顺带拿到图片附件的名字**（解决 P1-4 的根因）。
   **注意**：插件现在**同时**依赖磁盘布局（`attachments.ts` 构造 `hostPath` 给 `export_attachment` 的 `copyFile`）和官方 seam（下载/导出走 `readFileStream`）。这个双轨本身是设计张力点：`attachment-tool.ts:159` 直接 `copyFile(found.hostPath, ...)` 绕开了 `ctx.fs` 的文件系统抽象（注释自认「二进制附件走不了官方写通道」）。**建议**：`export_attachment` 改为 `readFileStream` → 经 `ctx.fs` 写，或明确记录这个绕行是刻意的、并把 `hostPath` 构造收敛到单点。

3. **（不推荐）自建附件库 / 换目录。**
   与内容寻址的宿主存储并行会破坏历史消息引用完整性（设计文档 §1 已正确论证「不做删除」）。否掉。

**关于「有没有更好的官方组件」**：我核对了宿主的全部相关包，可用官方设施与插件现状的对应关系是——

| 需求 | 官方是否已有 | 插件的做法 | 判定 |
|---|---|---|---|
| 家目录解析 | ✅ `dsh-home-paths` | 手写 | **应替换**（§2.1） |
| 路径祖先规范化 | ✅ `canonicalizeWatchPath` | 无（未涉及） | — |
| 字节流读取 | ✅ `AttachmentStore.readFileStream` | ✅ 已用 | 正确 |
| 附件列举/查询 | ❌ 无（只有 save/read） | 扫 `files/` | **正当补位** |
| 附件路径推导 | ✅ `storedFilePath(root, ref)`（`dsh-attachment-local/file-store`） | 手拼 `files/<sha2>/<sha>/<name>` | **应替换**——官方函数就是做这件事的，且带校验 |
| 下载文件名净化 | ✅ `fileLeafName(value)`（官方已处理 Windows 非法字符 + 反斜杠路径） | 手写 `sanitizeDownloadName`/`sanitizeFileNameForPath` | 服务端可复用；客户端仍需自己的（bundle 里带不进 node 侧） |

即：**`storedFilePath` 和 `fileLeafName` 是本次审查发现的、插件漏用的两个官方真源**，它们正好覆盖插件的两处手写（`attachments.ts:131,146` 的路径拼接、`ref.ts` 的净化）。这是「官方组件选型」的实质答案。

## 6. 做得好的地方（不返工）

- **安全栅栏设计扎实**：`fence.ts` 的 Host 信任（回环 + `trustedHosts`，裸 host 任意端口 / `host:port` 精确）、`ref.ts` 的 `sha256:<64hex>` 白名单、`sanitizeDownloadName` 的 CRLF/引号/反斜杠净化——我按对抗思路测了 DNS-rebinding 形状（`dsh.example.com.evil.com`）、路径穿越（`../../../etc/passwd`、`..%2f..%2fetc`、`\..\..\win`、U+202E）、头注入，**全部挡住**，且 `join()` 后确认无逃逸。
- **RFC 5987 双 filename**（`attachment-loop.ts:240-245`）：ASCII 回退 + UTF-8 `filename*`，中文名在浏览器侧正确落地。
- **下载路由的流式 + 背压处理**（:246-256）与错误码映射（404/409/413）是正确的，且区分了 `headersSent` 前后的失败。
- **`pageOf` 抽成纯函数**、测试覆盖 20 项新用例（fence/ref/净化/handle 降级/分页），**测试质量明显高于平均**——尤其 `handleText` 抛错降级、DNS-rebinding 形状这两条，说明作者想到了失败路径。
- **`isConcurrencySafe` 的判断有依据**（`attachment-tool.ts:138-139`：同 dest 由 `COPYFILE_EXCL` 互斥）。

## 6.5 附件库入口该放哪（0.6.2 的 UI 位置决策）

> **执行状态：已按方案 A 实施（2026-09-10）。** 附件库入口已从 `conversation.input.left` 移到
> `conversation.composer.dock`；面板改为输入卡下方的常驻折叠卡片，去掉四个硬编码摆位属性；
> 33 行 DOM 探针及 MutationObserver 已删除。构建 / 84 单测 / 源码类型检查全过，见 §6.5.4。

**结论：不该放在 `conversation.input.left`。你的判断是对的，而且官方槽位文档直接给出了更好的位置。**

### 6.5.1 官方槽位语义与当前放置相矛盾

`dsh-client-ui-conversation/lib/types/client/contract/slots.d.ts` 对每个槽位有明确注释，`input.left` 的定位是：

> `conversation.input.left` — **"Compact controls at the left of the composer tool row"**（输入框工具行左侧的**紧凑控件**）

而官方为「非紧凑的、环境性的、附加于输入区的内容」准备的是另一个槽位：

> `conversation.composer.dock` — **"Ambient entries below the composer card"**（输入卡下方的**环境性条目**）

实证两件事，都指向同一结论：

1. **官方占 `composer.dock` 的就是同类东西**。宿主 `dsh-client-ui-chat` 往这个槽位注册的是 `id: 'stats'` 的 `StatsPills`（会话步数/耗时/token 用量胶囊）——**附加信息面板**，正是「环境性条目」的范例。
2. **`input.left` 的行是紧凑控件条**。宿主 CSS 实测（`uV2eYG_tools`，0.1.5-rc.1）：
   ```css
   .uV2eYG_tools,.uV2eYG_modes,.uV2eYG_trailing{align-items:center;min-width:0;display:flex}
   .uV2eYG_tools,.uV2eYG_modes{gap:12px}
   .uV2eYG_add{width:28px;height:28px;border-radius:999px;...}
   ```
   这是一条 `gap:12px` 的横向图标按钮行，官方自己的回形针 `.add` 就在其中。**它是为 28px 图标按钮设计的，不是为「打开一个列表面板」设计的。**

而插件把**上传文件夹按钮**和**附件库按钮**打包在同一个槽位注册里（`InputTools`，`index.tsx:571-583`，两者同渲染于 `conversation.input.left`）。这两颗按钮的**性质根本不同**：

| | 上传文件夹 | 附件库 |
|---|---|---|
| 作用对象 | **当前这条消息**（追加进 composer 草稿） | **历史存量**（浏览/下载/导出全库） |
| 时机 | 发送前，一次性 | 随时，与草稿无关 |
| 生命周期 | 随草稿消费而消失 | 常驻 |
| 官方对应 | 回形针（同为 `input.left` 的紧凑控件）✅ | **StatsPills（`composer.dock` 的环境性条目）** |

**上传文件夹放 `input.left` 是对的**（它和回形针同类）；**把附件库塞进同一个槽位，是把「一个常驻的资源浏览器」当成了「一个操作当前草稿的按钮」**，这是位置与功能不匹配。

### 6.5.2 面板用 `position:fixed` 是位置错误的直接症状

因为槽位语义不匹配，面板没法在 `input.left` 里自然展开，只能**脱离文档流**：

```css
.dsh-files-dock{position:fixed;bottom:96px;right:16px;top:auto;z-index:9998;width:420px;max-height:60vh}
```

- `bottom:96px` 是**硬编码**的输入卡高度假设，输入卡变高（多行草稿、附件 rail 出现）就会错位。
- `right:16px` 把它钉在**浏览器视口**右下角，与输入框的水平居中布局无关——窗口一宽就飘到离输入框很远的地方。
- `z-index:9998` 是抢占式的层级声明。

对比官方 `composer.dock` 的容器 CSS（`_7yHdaG_dock`）：

```css
width:calc(100% - var(--dsh-composer-side-clearance) - ... - var(--dsh-composer-dock-inset) - ...);
max-width:calc(var(--dsh-composer-card-max-width) - ...);
margin:0 auto calc(0px - var(--dsh-composer-stack-gap) - 3px);
```

**官方用设计变量与输入卡对齐并居中，插件用硬编码像素与视口对齐。** 这两种写法就是「放在对的槽位」和「放在错的槽位再手动摆位置」的区别。

### 6.5.3 建议

**方案 A（推荐）：附件库入口移到 `conversation.composer.dock`，与 `StatsPills` 同区。**

- 语义正确（环境性条目），且自带官方布局变量，面板可改为**跟随输入卡列宽**的正常文档流元素，去掉 `position:fixed` / `bottom:96px` / `right:16px` / `z-index:9998` 四个硬编码。
- 位置稳定：输入卡变高、窗口变宽都不再错位。
- 代价：需重新调面板样式以适配该槽位的 `border-radius:12px 12px 0 0`（官方该区是「贴在输入卡下沿的卡片」形态）。

**方案 B（最小改动）：保留 `input.left`，但把附件库按钮与上传文件夹按钮拆开。**

至少诚实反映「上传是 input 操作、附件库是资源浏览」的分野；面板仍可用浮层，但**浮动锚点应改为相对输入卡容器**而非视口（`position:absolute` + 找输入卡做定位上下文），去掉 `bottom:96px` 这个硬编码。

**方案 C（也值得考虑）：放进 `conversation.session.header.utilities`。**

「右对齐的会话级工具」——附件库是会话级资源视图，语义上也站得住；官方注释明确该区是「Right-aligned Session utilities」。适合「希望它离输入区远一点、更像一个资源面板」的取向。

**不推荐**：留在 `input.left` 且维持现状。它把「常驻资源浏览器」伪装成「紧凑控件」，是 §6.5.2 那些硬编码样式的根因，而不是一个可以靠调 CSS 修好的细节。

**顺带一个已埋下的风险**：`installInputOrderProbe`（`index.tsx:529`，33 行）靠 DOM 特征（`[class*="_tools"]` + `[class$="_add"]` + `input[type=file]`）反推宿主 css-modules 哈希来维持插位。这套探测只在「必须挤进 `input.left`」时才需要——**按方案 A 移槽位后可整段删除**（`composer.dock` 是独立槽位，不需要与官方按钮争排序）。这与 §4 的「删复杂度优于搬运复杂度」是同一条判据。
